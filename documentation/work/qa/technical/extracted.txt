1 Propósito y alcance técnico
Este manual describe la arquitectura y la operación técnica de EcoData. Está dirigido a desarrolladores,
administradores de infraestructura y responsables de mantenimiento.
La aplicación integra gestión académica por colegio, registros de variables físicas, inventario de estaciones y
sensores, guías PDF, actividades de Diario de Campo y calendario ambiental. El servidor entrega HTML
mediante Blade; las interacciones auxiliares consultan rutas JSON para listas dependientes. No se identificó una
API de ingestión automática de estaciones ni una aplicación móvil independiente.
La revisión abarca código, migraciones, dependencias bloqueadas, rutas y configuración. La aplicación y su
suite de pruebas no se ejecutaron durante esta revisión. Los procedimientos de instalación y operación deben
validarse en el entorno independiente descrito antes de aplicarlos a una instalación con datos.

Las restricciones o defectos encontrados se detallan al final. Son relevantes para explicar el estado actual y para
evitar que el manual prometa prestaciones incompletas, por ejemplo la importación CSV de mediciones o el
envío de reportes por correo.

4 Configuración del entorno
La configuración se obtiene de config/*.php y variables de entorno. No existe src/.env.example en la
copia revisada, aunque composer setup intenta copiarlo.
Para una instalación nueva, crear src/.env a partir de un inventario revisado, sin copiar credenciales de otro
ambiente. Definir credenciales nuevas y hacer coincidir la configuración de MySQL en Compose con
DB_DATABASE, DB_USERNAME y DB_PASSWORD. Los valores de demostración incluidos en compose.yaml
deben sustituirse en una configuración local o de despliegue controlada; modificar .env por sí solo no
reemplaza los valores literales de ese archivo. Si ya existe .env, conservarlo y revisar sus claves de forma
controlada; no sobrescribirlo con esta plantilla.
APP_NAME=EcoData
APP_ENV=local
APP_KEY=
APP_DEBUG=true
APP_URL=http://localhost:8081
APP_LOCALE=es
APP_FALLBACK_LOCALE=en
DB_CONNECTION=mysql
DB_HOST=mysql
DB_PORT=3306
DB_DATABASE=EcoData_db
DB_USERNAME=<usuario_definido_para_este_entorno>
DB_PASSWORD="<secreto_nuevo>"
SESSION_DRIVER=database
CACHE_STORE=database
QUEUE_CONNECTION=database
FILESYSTEM_DISK=local
MAIL_MAILER=log
MAIL_FROM_ADDRESS=notificaciones@example.invalid
MAIL_FROM_NAME=EcoData
Este bloque es una plantilla conceptual: los marcadores <...> se reemplazan antes de ejecutar. APP_KEY se
genera con Artisan una sola vez para el ambiente. MAIL_MAILER=log evita envíos reales durante preparación,
pero los logs pueden contener datos personales o contraseñas temporales; limitar su acceso y retención. El
nombre de la base debe concordar con el servicio MySQL.

5 Instalación inicial propuesta
El procedimiento está destinado exclusivamente a una copia aislada del código y a un proyecto Docker
nuevo con volumen nuevo. La configuración fija name: ecodata; por ello ejecutar Compose sin -p
puede reutilizar los datos de una instalación existente.
1. Preparar una copia independiente del código en otra carpeta. No reutilizar ni sobrescribir el .env de la
 instalación existente. Abrir terminal en el src de la copia; confirmar Docker/Compose, espacio y puertos
libres.
2. Elegir un nombre de proyecto nuevo. En este ejemplo se usa ecodata-validacion: comprobar docker
 compose -p ecodata-validacion ps -a y docker volume ls --filter
label=com.docker.compose.project=ecodata-validacion. Si aparece cualquier recurso previo, elegir otro
nombre y usarlo en todos los comandos. Crear .env propio y configurar credenciales nuevas de MySQL.
3. Construir la imagen PHP e iniciar MySQL. Esperar a que el servidor acepte conexiones; revisar logs si la
 inicialización del volumen sigue en curso.
4. Instalar dependencias con composer.lock y compilar los recursos con package-lock.json. Configurar
 permisos de escritura en storage y bootstrap/cache para el usuario que ejecuta PHP-FPM.
5. Generar APP_KEY si la instalación es nueva; ejecutar migraciones sin --seed. Cargar únicamente los roles y
 permisos con la clase explícita RolesAndPermissionsSeeder.
6. Crear una cuenta inicial controlada con super_admin y contraseña propia. Iniciar sesión para registrar
 colegio, grados, cursos y usuarios; validar la asignación antes de cargar contenido.
7. Crear el enlace público de almacenamiento, iniciar app y nginx y revisar /up, /login y los recorridos críticos
 por rol. Mantener los servicios auxiliares solo cuando se necesiten.

conservar. DatabaseSeeder invoca EcoDataDemoSeeder, cuyo primer paso trunca tablas de usuarios, roles y
módulos. Los seeders iniciales/demostrativos también contienen credenciales predefinidas; no constituyen un
proceso seguro de aprovisionamiento productivo.
Cuenta inicial
Abrir php artisan tinker dentro del contenedor, crear un User con nombre, correo controlado y una contraseña
única almacenada mediante Hash::make, y asignar el rol super_admin mediante assignRole. Esta cuenta puede
iniciar sin school_id. Introducir el secreto de forma interactiva y evitar incluirlo en archivos del repositorio,
capturas o historial compartido. Confirmar que el correo y el rol corresponden a la persona responsable. No
usar los ejemplos de seeders como credenciales definitivas.
Durante el cierre de instalación registrar: revisión Git, versiones reales, fecha, responsable, estado de
migraciones, URL, cuentas de prueba usadas, comportamiento de carga/descarga y resultados de seguridad.
Una respuesta correcta en /up confirma la ruta de salud, pero no sustituye estas comprobaciones.

Relación
Cardinalidad y comportamiento
Categoría → variables
Categoría global, compartida entre colegios. La FK de variable restringe su eliminación
si se usa.
Registro físico → valores
Un registro contiene múltiples valores; UQ por registro y variable; eliminar el registro
elimina sus valores.
Estación → sensores
Una estación contiene múltiples sensores; eliminación en cascada. Registros y
actividades conservan datos con weather_station_id en NULL al borrar estación.
Actividad → preguntas y entregas
Una actividad contiene preguntas ordenadas y una entrega por usuario; eliminación
en cascada.
Entrega → respuestas
Una respuesta por pregunta y entrega; las respuestas se eliminan con cualquiera de
sus padres.
Evento → reconocimientos
UQ por evento y usuario; representa haber leído/reconocido el evento.
El alcance por colegio se implementa principalmente mediante filtros y comprobaciones en PHP. Las FK
simples comprueban que los identificadores existan, pero no garantizan por sí solas que todos los
identificadores de una fila pertenezcan al mismo colegio. Las restricciones de aplicación y las pruebas de
aislamiento son necesarias.
No se identificó uso general de SoftDeletes ni una bitácora de auditoría de cambios. Borrar entidades puede
eliminar contenido dependiente de forma definitiva. Desactivar una entidad mediante is_active es distinto de
eliminarla; su efecto concreto depende de cada consulta y no equivale a revocar universalmente una sesión.

User incorpora Notifiable y HasRoles. Convierte password con el cast hashed, is_active a boolean y
email_verified_at a datetime; password y remember_token se ocultan al serializar. Declara relaciones con
colegio, grado, curso, estaciones responsables, eventos creados, reconocimientos, actividades, entregas y
revisiones.
Los roles no son una columna de users. Spatie utiliza roles, permissions, model_has_roles,
model_has_permissions y role_has_permissions. Las dos primeras tienen id, name, guard_name y timestamps,
con unicidad name+guard_name. Las pivotes relacionan identificadores de rol/permiso con model_id y
model_type o entre roles y permisos. config/permission.php define sus nombres y estrategia de caché.
La eliminación de un usuario conserva registros físicos con user_id NULL, pero las entregas y reconocimientos
se borran en cascada. Las guías creadas por ese usuario también tienen FK cascade. Por ello el procedimiento
de retiro debe evaluar dependencias y respaldo antes de usar la acción Eliminar.

 100 y retroalimentación; se registra revisor y reviewed_at y se intenta notificar al estudiante.

21 Respaldo y restauración verificable
No se identificó automatización de backup en el repositorio. Debe incorporarse un procedimiento
institucional con retención, cifrado, responsables y pruebas de recuperación.
El conjunto mínimo incluye una exportación consistente de MySQL, storage/app/private, storage/app/public, la
revisión del código y archivos lock, configuración de despliegue y una copia protegida de .env/APP_KEY. No
basta con copiar el volumen de MySQL mientras está escribiendo. No compartir dumps ni logs porque
contienen datos personales.
1. Definir una carpeta de backup con acceso restringido y fecha/revisión. Verificar espacio libre y confirmar
 que se apunta al ambiente correcto.
2. Poner la aplicación en mantenimiento y pausar escritores externos/colas si existen. Tomar una exportación
 lógica de MySQL y copiar los dos árboles de archivos durante la misma ventana.
3. Guardar manifiesto de revisión, estado de migraciones, tamaños y checksums. Proteger
 configuración/secretos mediante el almacenamiento seguro de la organización, separado de la entrega
pública.
4. Reactivar la aplicación y comprobar el servicio. Replicar la copia a un destino independiente según la
 política aprobada.
5. Restaurar periódicamente en una instancia aislada, con correo real deshabilitado. Comparar conteos,
 integridad referencial, archivos y recorridos funcionales.
6. Documentar duración de recuperación, punto de recuperación alcanzado, errores y responsable. Solo una
 restauración satisfactoria demuestra utilidad del backup.
Ejemplo de exportación lógica en Docker
Estos comandos son una plantilla para Bash/WSL y MySQL; ejecutarlos dentro de un procedimiento validado.
La opción -p solicita la contraseña interactivamente. Sustituir la base si el ambiente usa otro nombre. Guardar

docker compose cp mysql:/tmp/ecodata.sql ./backup/ecodata.sql
